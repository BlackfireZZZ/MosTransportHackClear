# Паспорт данных, target и прогнозной модели TramFlow

Дата: 25 сентября 2026. Состояние: реальные данные организаторов, обученный маршрутный
CatBoost и экспериментальный ансамбль. Это специализированное ML-прогнозирование;
универсальный интеллект AGI не реализован. Документ описывает фактически полученные
файлы и текущие вычисления, отдельно отмечая допущения и ещё не реализованные части.

## 1. На какой вопрос отвечает модель

«Сколько успешных валидаций будет на маршруте R в календарный час H московской даты D?»
Выход — одно неотрицательное целое число на маршрут и час, суммарно по направлениям,
трамваям, остановкам и типам билета. Единица: событие успешной валидации.

Организаторы называют это `boardings` — посадки. В приложении точная семантика:
`target=validation_count`, `unit=event_count`. Нет наблюдения выхода пассажира,
поэтому загрузка салона, число людей внутри вагона и процент вместимости из этого
target не следуют. Один человек может совершить несколько валидаций; уникальные
карты также не равны уникальным людям. Прогноз 100 означает 100 успешных событий
за час на всём маршруте, а не 100 пассажиров одновременно в одном вагоне.

Входная история: 1 января–31 октября 2025. Требуемый файл решения: 1 ноября–31 декабря 2025,
61 день × 24 часа × 10 маршрутов = **14640 значений**. Скрытые факты этого периода
не предоставлены; строки ноябрьского хвоста raw намеренно исключены из обучения.

Широкая продуктовая постановка также требует день/месяц/год, остановки и карту.
Фактические конкурсные labels дают только маршрут×час. Выполненные маршрутные
эксперименты не доказывают качество остановочного/годового прогноза или live-карты.

## 3. Словарь сырых событий: все 14 полей

CSV: UTF-8, разделитель`;`, первая строка заголовок. Типы ниже — логический смысл,
а не обещание чистого типа каждой raw-ячейки. Идентификаторы следует сохранять как
непрозрачные строки, не отбрасывая возможные ведущие нули.

| Поле | Смысл по README источника | Роль в текущем ML и ограничения |
|---|---|---|
| `tran_no` | Номер транзакции/id события | Не признак; глобальная уникальность не доказана, dedup не применяется |
| `device_no` | Идентификатор валидатора | Не признак; не считать остановкой или стабильным vehicle_id без crosswalk |
| `tran_date_time` | Дата-время валидации | Основное event time; источник даты и часа target |
| `begin_date_time` | Дата-время начала поездки, служебное | Не используется; качество/связь с отдельной поездкой не проверены полностью |
| `input_date_time` | Заявленное время загрузки | Исключено: ненадёжные будущие даты; не доступность события для модели |
| `crd_hashcode` | Обезличенный хеш карты | Не используется для target/признаков; различимые карты не равны людям |
| `validation_result` | Код результата;1=успех, остальные=отказ | Единственный фильтр успешности target |
| `tran_type_id` | Код типа транзакции,52 основной проход | Не фильтр target: другие успешные типы тоже считаются |
| `place_id` | Код площадки/депо | Не stop_id; не участвует в маршрутном target |
| `good_type` | Билет/тариф | Не используется; будущий тарифный состав неизвестен |
| `pass_route` | Зашумлённая цепочка пересадок | Не источник номера маршрута и не достоверная OD-разметка |
| `ngpt_route` | Номер и тип маршрута, например «25 трамвай» | Источник route=25; проверяется разрешённый набор маршрутов |
| `bus_exit_no` | Номер выхода/графика ТС | Не используется; сам по себе не идентифицирует поездку/остановку |
| `garage_number` | Гаражный/бортовой номер трамвая | Не используется; нет доказанной временной связи с расписанием и телематикой |

Коды отказов наблюдаются, но их отдельная бизнес-расшифровка не предоставлена.
Не называем конкретный код «недостаточно средств» без справочника. Сырые номера
транзакций, карт и устройств не нужны в публичном отчёте и модельном артефакте.

## 4. Как точно собирается target

Для разрешённого маршрута r, московской даты d и часа h:

```text
y[r,d,h] = SUM по raw-строкам i (
    validation_result[i] == 1
    AND route_from(ngpt_route[i]) == r
    AND MoscowDate(tran_date_time[i]) == d
    AND MoscowHour(tran_date_time[i]) == h
)
```

Это `COUNT(*)` после фильтра, а не `COUNT(DISTINCT crd_hashcode)`, сумма тарифа,
число типов 52 или количество записей labels. Интервал часа полуоткрытый:
08:00:00 включён,09:00:00 относится к следующему часу. Временная политика проекта
Europe/Moscow; raw timestamp не несёт самостоятельной информации об offset.

Воспроизводимая последовательность:

1. Читать **объединение** train.csv и test.csv без изменения оригиналов.
2. Разобрать tran_date_time и номер из ngpt_route; проверить допустимые значения.
3. Оставить validation_result==1 и события в `[2025-01-01 00:00,2025-11-01 00:00)`.
4. Сгруппировать по `(route, date, hour)`, считать строки.
5. Сопоставить с объединением двух файлов labels по полному ключу.
6. Построить полную сетку 10×304×24 и заполнить отсутствующие ключи нулём
   **успешных событий в этой выгрузке**, сохранив оговорку о неизвестной полноте.

Условный пример: за 08:00–09:00 у маршрута 17 три строки с результатом 1 и две с
отказом. Target=3, даже если две успешные строки относятся к одной карте.
Этот пример иллюстративный, не раскрывает реальные строки.

| Проверка target | Измеренный результат |
|---|---:|
| Сумма train labels | 46912710 |
| Сумма test labels | 12754481 |
| Сумма target за январь–октябрь | **59667191** |
| Положительные ключи labels | **57551** |
| Полная сетка | **72960** |
| Отсутствующие в labels ключи, заполненные 0 | **15409** |
| Несовпадения raw union и labels | **0** |

Почему нельзя агрегировать каждый raw-файл независимо: train.csv содержит 523
успешных события раннего 1 сентября на 15 ключах. Они относятся к сентябрьскому target.
В test.csv есть 562 успешных события 1 ноября на 12 ключах — они вне допустимой истории.
Поэтому `test` успешных строк 12754520, но test labels sum12754481:
12754520 − 562 + 523 = 12754481. Дата события важнее имени файла.

Идентичность raw→labels доказана для определения источника. Она не доказывает
отсутствие повторной доставки транзакций: глобальный dedup по tran_no не выполнялся.
Менять dedup-политику без нового определения target нельзя — перестанут совпадать labels.

## 5. Покрытие, нули и качество

Маршруты прогнозирования:1,5,7,11,12,17,25,26,28,50. В labels положительные
значения только у девяти. Маршрут 5 имеет одну найденную raw-строку 29 октября с
результатом 30, ни одного успеха. Его модельный прогноз 0 — явная политика при
отсутствии положительной истории, а не доказательство отсутствия реального спроса.

Отсутствие label может означать отсутствие успехов, отсутствие движения или
неполную выгрузку. По текущим данным эти причины не различить. Среди остальных
маршрутов выявлен нулевой день у 50:21 сентября. Не объявляем его закрытием линии.

В полном EDA проверялись шесть полей: tran_date_time, input_date_time,
validation_result, tran_type_id, place_id, ngpt_route. Некорректных event timestamps
не найдено; пропусков этих полей, кроме 155 place_id в train, нет. В input_date_time
есть 21270 дат 2026 при событиях 2025. Полная валидность остальных восьми полей,
уникальность карт/транзакций и корректность каждой связи между справочниками не доказаны.

Допущение backtest: вся историческая разметка до origin уже доставлена. Нет честного
available_at/delivery watermark; это **retrospective perfect delivery**, не измеренная
online-доступность. Во время реального запуска нужны отдельные сведения о задержке.

## 6. Справочники: поля, связи и допустимое использование

Первые пять листов большого XLSX: строка 1 — выборочные пояснения, строка 2 — реальные
имена колонок. В листе с координатами заголовок уже в строке 1. GTFS в имени листа
не доказывает соответствие стандартному GTFS-feed: есть собственные поля и коды.

### 6.1 Маршруты GTFS_ROUTES —10 строк

| Поле | Значение |
|---|---|
| `route_id` | Внутренний ID справочника; не номер маршрута и не ID нашей БД |
| `reg_num` | Реестровый номер в системе |
| `route_short_name` | Номер маршрута; кандидат для явного crosswalk к label route |
| `route_long_name` | Полное название маршрута А–Б |
| `route_desc` | Описание/категория; полного словаря нет |
| `status` | Статус, например «открыт»; полного словаря нет |
| `route_view` | Вид/характер маршрута, например «Постоянный» |

### 6.4 Порядок_с_координатами —622 строки

Все 14 полей предыдущего листа плюс `stop_name`, `stop_lat`, `stop_lon`.
Удобно для геометрии и карты, но это не координаты вагона во времени и не target.
Связи route_id→маршрут, stop_id→остановка логически ожидаемы по схеме; полная
проверка referential integrity, исторических версий и всех неоднозначностей пока
не является частью обучающего pipeline.

### 6.8 Другие данные приложения

Существующий OSM-граф в `data/` — отдельный источник геометрии, не часть организаторских
labels. Он не даёт исторического числа валидаций или координат транспорта в реальном
времени. Демонстрационные данные приложения и synthetic fixtures остаются отдельными
от реального обучения. Никакие seed-прогнозы, значения sample submission или synthetic
stop labels не добавлялись к обучающему target.

## 7. Labels и модельная таблица

| Колонка labels | Тип/ограничение | Назначение |
|---|---|---|
| `route` | int из фиксированного набора 10 номеров | Ключ сущности |
| `date` | ISO YYYY-MM-DD, внутри периода файла | Календарная дата |
| `hour` | int0…23 | Календарный час |
| `boardings` | int≥0 | Целевая величина y |

Текущий loader отвергает иной header, неизвестный маршрут, неверный час/дату,
отрицательные значения, дубли ключей и пустую совокупную выборку. Массив имеет форму
`[304days,10routes,24hours]`, float64 для вычислений. Порядок маршрутов строго
`(1,5,7,11,12,17,25,26,28,50)`; внутренний feature route — его индекс 0…9, не DB ID.
Проверка качества поставки и сертификация отсутствующих данных в loader не реализованы.

## 8. Какие признаки идут в модель

Выбранный одиночный CatBoost использует **только шесть календарных признаков**:

| Признак | Формирование | Известен на дату будущего прогноза |
|---|---|---|
| `route` | Индекс номера в фиксированном списке маршрутов | Да |
| `hour` | Час 0…23 прогнозируемого bucket | Да |
| `weekday` | День недели 0=понедельник…6=воскресенье | Да |
| `day_type` | 0 рабочий,1 обычная суббота,2 воскресенье/выходной из списка | Да, при заранее опубликованном календаре |
| `july_august` | Месяц 7 или 8 | Да; это не доказанный календарь школьных каникул |
| `holiday` | Включение в принятый OFF, включая перенесённые выходные | Да; признак означает список OFF, не только государственный праздник |

Первые 4 передаются CatBoost как категории. one_hot_max_size24 покрывает все их
значения, поэтому выбранный эксперимент не доказывает преимущества target encoding.
Календарь ограничен 2025; учтён рабочий день 1 ноября и переносы выходных. Источник и
дата публикации зафиксированы в `features.py` и отчёте первого эксперимента.

Модель учит типичный профиль маршрута/часа/типа дня по всей истории до origin.
У неё нет отдельного тренда по абсолютной дате или month, нет lag-target на входе
победившего estimator. Поэтому при одинаковых шести признаках результат одинаков
для разных дат: это ограничение представления сезонности, а не динамическая симуляция.

Также были проверены, но не входят в выбранный одиночный estimator:

| Семейство признаков | Точный смысл |
|---|---|
| `month`, `lead_days` | Месяц цели; номер дня прогноза 1…61 |
| `week1/2/4/8` | Среднее того же route/hour/weekday в последних 7/14/28/56 днях **до origin** |
| `type4` | Среднее route/hour для соответствующего day_type за последние 28 дней |
| `median4` | Медиана route/hour/weekday за 28 дней |
| `ratio1/2/8` | week1/2/8, делённое на max(week4,20) |
| `routelevel7/28` | Среднее суточное число успешных событий маршрута за 7/28 дней |

Все профили заморожены на origin; после него фактические lag-и не подставляются.
Snapshot-кандидаты обучаются на прошлых origins с шагом 7 дней и максимум 61 целевым
днём, причём и X, и y целиком лежат до training cutoff. Перекрывающиеся snapshots
не являются независимыми наблюдениями и не используются для random split.

Не используются: хеш карты, персональные/служебные ID, input_date_time, неизвестные
будущие факты погоды, справочники 2026, sample predictions. Добавление таких данных
без проверки доступности и смысла не превращает модель в более сильную.

## 9. Обучение, проверка и честная интерпретация метрики

Одиночный cat_native: CatBoost1.2.10,800 итераций,depth8,learning_rate0.06,MAE,
seed42,4 потока,has_time=True, без early stopping по проверяемому будущему.
Три development origins:1 апреля,1 июня,1 августа 2025, горизонт каждого 61 день.
Отбор 24 кандидатов по pooled score с условием выигрыша≥.01 у week1 на каждом origin.

```text
WAPE = sum(abs(y - prediction)) / sum(y)
score = max(0, 1 - WAPE)
```

Считается на исходных counts после такого же округления, как у выходного прогноза.
Это не среднее MAPE по строкам и не среднее route-WAPE. Большие маршруты сильнее
влияют на общий результат. Если весь срез y=0, WAPE не определён; показывается
абсолютная ошибка, не искусственный идеальный score. Нулевые часы внутри ненулевого
среза корректно входят в числитель общей метрики.

| Модель | 1 апреля,61 день | 1 июня,61 день | 1 августа,61 день |
|---|---:|---:|---:|
| Week1 | .783474 | .761602 | .780640 |
| Week4 | .811799 | **.805483** | .802354 |
| CatBoost MAE | .859343 | .792905 | .865402 |

Замороженный MAE-кандидат на октябре при origin1 сентября: score.866016,
WAPE13.3984% против week1 score.813883/WAPE18.6117%. Сентябрь пересекается с августовским
development и повторно использовать его как независимый holdout нельзя. Даже октябрь
ранее изучался в EDA; это пост-отборная проверка первого цикла, не полностью слепой тест.
Качество ноября–декабря по скрытым labels неизвестно. Значение baseline≈.48 из README
организаторов — их утверждение о скрытом периоде, а не наш измеренный результат.

Защита от утечки проверяется изменением будущих labels: до-origin features и прогноз
не должны меняться. Дополнительно проверены временные границы, календарные переносы,
валидность сетки, отсутствие отрицательных/NaN и равенство inference после reload.

## 10. Дополнительная модель: ансамбль двух CatBoost

Второй цикл не добавляет неизвестные данные или новые зависимости. Проверены 9
фиксированных сочетаний MAE-CatBoost с RMSE-CatBoost, type4 или week4, с долей второго
компонента 25%,50%,75%. Выбор только по трём прежним development origins; это повторный
подбор на тех же данных, с растущим риском переобучения самого процесса выбора.

Победитель по pooled score: **50% cat_native + 50% cat_native_rmse**. Обе модели
имеют одинаковые 6 признаков и бюджет 800 деревьев/depth8; отличается loss.
Компоненты сначала выполняют свой clipping/округление и правило нулевой истории;
их значения усредняются и снова округляются `np.rint` (ties-to-even). Усреднение
сырых вещественных выходов было бы другим экспериментом.

## 11. Что хранится на выходе и как это читает приложение

Ключ прогноза: `(route number,bucket_start)`; timestamp с offset, московский час.
`route-forecast.experimental.v1` требует ровно 14640 уникальных точек полного 61-дневного
окна и десяти разрешённых маршрутов. Неизвестные поля, дубли, пропуски, некорректные
времена, отрицательные и неконечные значения отвергаются.

| Метаданные | Смысл |
|---|---|
| `schema_version` | Версия структуры route-forecast.experimental.v1 |
| `scope` | route_all_directions: сумма по всем направлениям |
| `target`, `unit` | validation_count, event_count |
| `synthetic`, `status` | false, experimental: реальные labels, экспериментальный прогноз |
| `timezone` | Europe/Moscow |
| `run_id`, `model_version` | Идентификаторы результата и версии модели |
| `dataset_id`, `source_version` | Идентификатор январь–октябрьского источника |
| `source_hash` | SHA-256 двух label-файлов с именами; отличается от hash всего ZIP |
| `feature_version` | route-calendar-profiles.v1 |
| `forecast_origin` | Момент отсечки прогноза,2025-11-01T00:00:00+03:00 |
| `data_cutoff` | Верхняя исключённая граница использованной истории; равна origin |
| `generated_at` | Фактическое время запуска вычисления, здесь 2026; не маскируется под 2025 |
| `points` | route,bucket_start,predicted для каждого часа |

Это ретроспективный выпуск для конкурсного периода 2025, сформированный сейчас.
Внутри сохранённого bundle: бинарные модели, конфигурации, история/профили,
forecast.json,submission.csv,manifest с хешами. Для ансамбля две директории
компонент. Бинарники игнорируются Git; код и отчёты версионируются. Загрузка
рассчитана на доверенные локальные bundles, не на произвольный пользовательский файл.

| Представление | Преобразование | Проверенное покрытие |
|---|---|---|
| Конкурсный CSV | route;date;hour;prediction | Все 10 маршрутов,61 день,24 часа |
| День в API | 24 почасовые точки выбранной даты | Даты в пределах bundle |
| Месяц в API | Суммы 24 часов каждого календарного дня | Ноябрь 30 дней,декабрь 31 день |
| Год | Не поддерживается данным bundle | Нельзя продолжать 61 день до 365 заполнением |
| Остановка/направление | Не поддерживается моделью | Нет соответствующего target |

Проверка совместимости преобразует реальный artifact в существующие
ForecastSnapshot→ForecastMapService→ForecastResponse и обратно через JSON.
Контролируются ключи, суммы, target/unit, происхождение и временные метки.
В тесте mapping номера маршрута в serving ID явный, но искусственный; реальные
ID каталога приложения ещё не разрешены. Поля capacity и bounds остаются null,
остановки пустыми; маршрутный artifact не содержит stop_points, поэтому map positions отсутствуют.
Для статической карты нужна проверенная геометрия/crosswalk, а live feed — отдельная возможность.

**Приложение ещё не переключено на этот реальный model run.** Для этого нужны:
явный registry route number→serving ID; согласованный route-only publisher;
атомарная публикация полного bundle; выбор run по покрытию даты; проверка
artifact=DB=API=график/CSV на живом стенде. Факт наличия Python-интерфейса
ForecastModel не означает, что backend автоматически обучает/загружает эту модель.
Training остаётся вне online worker. Backend/frontend в этих экспериментах не менялись.

## 12. Что собирать дальше и для какого target

Ниже требования к будущим данным, а не уже подключённые источники.

| Данные | Минимальные поля/связи | Какую возможность дают |
|---|---|---|
| Доставка событий | event_time,available_at,source_watermark,coverage,revision | Честный backtest доступности, различение отсутствия фактов и задержки |
| Выполнение рейсов | dated trip_id,route,direction,vehicle,start/end,cancellations | Отличать изменение предложения транспорта от изменения спроса |
| Валидатор↔вагон↔рейс | IDs с valid_from/valid_to и проверкой неоднозначностей | Связывать оплаты с конкретным выполненным рейсом |
| Телематика | vehicle_id,time,lat/lon,accuracy,route/trip binding | Историческое сопоставление события с движением; live feed отдельно |
| Остановочные события | stop_id,trip/vehicle,time,board/alight,quality | Обучать остановочный target; occupancy потребует входы и выходы |
| Вместимость | vehicle/model,число,единица,период действия | Осмысленный load%; категорий ОБК недостаточно |
| История сети | версии маршрута/остановок/геометрии и даты публикации/действия | Учитывать перестройки без использования будущей информации |
| Погода/ремонты/мероприятия | forecast/publication_time и effective_time | Только известные на origin внешние признаки и измеренная абляция |
| Несколько полных лет | Сопоставимые targets и изменения источника | Проверять годовую сезонность и долгосрочный горизонт |

Для остановочного или onboard target потребуется новое определение разметки,
отдельные тесты соответствия и проверка качества. Нельзя просто поделить маршрутный
час на число остановок или вместимость одного вагона. При наличии только текущих
данных следующая полезная работа — publisher и оценённые интервалы, а не обещание AGI.

### Загрузка сохранённого ансамбля без повторного обучения

Обычный `tramflow-route-ml predict` принимает одиночный bundle. Корневой каталог
ансамбля ему не подходит: нужно загрузить две компоненты и применить тот же reducer.
Готовый forecast.json при этом полностью совместим с экспериментальным route artifact.

```python
from pathlib import Path
import numpy as np
from tramflow_ml.route_models.models import Trained

bundle = Path("ml/artifacts/route-ml-2025-ensemble-reviewed")
mae = Trained.load(bundle / "cat_native")
rmse = Trained.load(bundle / "cat_native_rmse")
predictions = np.rint((mae.predict() + rmse.predict()) / 2)
# Shape: 61 days × 10 routes × 24 hours, fixed route order from section7.
```

Эта формула также проверена по всем сохранённым точкам и CSV независимым ревью.
