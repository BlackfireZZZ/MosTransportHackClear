# Исторические расписания и первая остановка: проверка абсолютного времени

Найдены и распарсены архивные страницы 2025 года и GTFS с 1798 рейсами маршрутов
11, 12, 17. Реализовано сопоставление с конкретной последовательностью `trip_id`,
абсолютным временем и предпочтением первой остановки. Предпочтение конечной
улучшает согласованность временных интервалов в эксперименте, однако контроль
со сдвинутыми часами и чувствительность к параметрам не подтверждают точную
локализацию. Результаты остаются гипотезами; новые hard labels не опубликованы.

## Проверяемый алгоритм

Наблюдения — первые секунды кандидатов посадки, первая оплата обязательна.
Выбор рейса учитывает route_type=tram, номер маршрута, календарь, направление и
service day. Время >24:00 не берётся по модулю: рейсы предыдущих суток остаются
кандидатами около полуночи. Часы наблюдений — Europe/Moscow. Начало показанного
окна и начало сессии НЕ объявлены началом рейса.

Для кандидата `рейс r, начальная позиция j` фиксируется
`offset = первая оплата − время расписания(r,j)`. Допуск |offset| <=900с.
Offset включает эксплуатационное отклонение и неизвестную задержку оплаты;
это не чистая оценка опоздания. Он не переоценивается независимо на каждой остановке.

Стоимость в секундах:

`clock_weight × |offset| + start_prior × [j != 0]`

плюс для каждого последующего наблюдения:

`|фактический интервал − интервал выбранных остановок рейса|`

`+ residual_weight × |фактическое время − расписание − offset|`

`+ 15 × число пропущенных остановок`.

Разрешены шаги 1..6, только вперёд внутри одного GTFS-рейса. Смена направления,
новый оборот, ложные промежуточные всплески и отдельная модель плавной задержки
в этой ограниченной версии не реализованы. При отсутствии пути возвращается отказ.
Первая позиция означает первую строку stop_times: пустой pickup_type источника
не доказывает, что это фактическая первая посадочная платформа.

Шесть вариантов заданы заранее как ablation, без выбора «победителя» для обучения:

| Вариант | Вес абсолютного offset | Предпочтение первой позиции | Вес остаточного отклонения |
|---|---:|---:|---:|
| Интервальный baseline | 0 | 0 | 0 |
| Только часы | 0.2 | 0 | 0.25 |
| Часы + мягкая H0 | 0.2 | 60с | 0.25 |
| Часы + сильная H0 | 0.2 | 180с | 0.25 |
| Больший вес часов | 1 | 60с | 0.25 |
| Принудительная H0 | 0.2 | Только первая позиция | 0.25 |

Baseline использует те же рейсы и допуск ±900с, но не вознаграждает близость часов.
Это уже ограниченный по времени baseline; его нельзя считать старым неограниченным
подбором по всему циклу. Частые равные стоимости дают произвольный выбор среди
альтернатив. Разрыв стоимости и число вариантов не являются вероятностями.

## Протокол реальных данных и результат

Те же 36 сессий rank0 из замороженного исследования: три маршрута, 12 дат
15-го/18-го числа мая–октября 2025. Для каждой сохранены самое плотное 30-минутное
окно и первые 30 минут фактических записей сессии (72 сегмента). Плотное окно:
3 прежних детектора; начало сессии: adaptive. Всего 144 потенциальных сочетания.
Первые оплаты восстановлены из проверенных исходных date shards; относительные
времена dense-окон побитно сверены с прежним экспериментом. Пороги детекторов
заморожены на январе–апреле, повторного обучения нет.

Не менее 6 начал есть в 87 сочетаниях, представляющих 35 разных сегментов.
57 сочетаний исключены с явной причиной; из первых 30 минут сессий проходят только
3/36. Поэтому проверка H0 преимущественно относится к произвольным dense-окнам,
а не к подтверждённым началам рейсов. Пять сессий начинаются до 04:00, возможна
обрезка суточной границей. Из 36 первых оплат 13 лежат в пределах минуты от
какого-либо отправления с конечной, 24 — в пределах трёх минут; в 3 случаях
нет конечной в пределах 15 минут. Медиана |offset| среди 33 найденных —82с.
Это близость к расписанию, не подтверждение нахождения на конечной.

Для выбора рейса используются только первые 4 начала. Затем `trip_id`, последняя
позиция и offset фиксируются; следующие 2–4 начала сопоставляются только вперёд
в том же рейсе. Будущие времена ещё участвуют в выборе пропущенных остановок:
это проверка ограниченного продолжения, НЕ безусловный прогноз. Детекторы используют
окрестность всего окна, поэтому эксперимент offline, не причинная online-оценка.

Сравнение на одинаковых успешно продолженных сочетаниях:

| Вариант | Парных сочетаний | MAE baseline, с | MAE варианта, с |
|---|---:|---:|---:|
| Только часы | 78 | 61.32 | 60.10 |
| Часы + мягкая H0 | 80 | 60.55 | 42.01 |
| Часы + сильная H0 | 81 | 61.63 | 29.63 |
| Больший вес часов | 78 | 61.32 | 51.78 |
| Принудительная H0 | 81 | 61.63 | 29.10 |

Число выбранных первых позиций из87: baseline1, только часы3, мягкая H0 63,
сильная H0 85, больший вес часов30, принудительная H0 87. Большая зависимость от
штрафа означает влияние предположения, не обнаружение стольких реальных начал.
Начальные позиции также оставляют разное количество остановок для продолжения,
что влияет на ошибки и отказы; сравнение не измеряет точность локализации.

Контроль мягкой H0: сдвиг всех времён на7мин даёт MAE45.91с против40.61с реальных
часов на86парах. Но сдвиг на17мин даёт37.72с против40.99с на84парах. Значит,
доказанного устойчивого преимущества правильного абсолютного времени здесь нет.
Нельзя объявлять двукратный выигрыш точности определения остановок.

Пример №17, 15.05, dense adaptive: только часы выбирают «МФЦ Южное Медведково»,
offset−17с; мягкая H0 — «Останкино», offset−77с. Последующие ошибки мягкой H0:
−15,+1,−9,−44с. Хорошие интервалы не исключают другой участок/направление.
Подробности по маршрутам, месяцам, вариантам и отказам: [summary.json](summary.json).

## Какие остановки устойчивы

Сохранены [stations.json](stations.json): 184 назначения adaptive-кандидатов
(первое обязательное наблюдение исключено) на107разных ключей route/direction/stop.
Ни одно из184назначений не сохраняет один stop_id одновременно во всех четырёх
вариантах весов/предпочтений. Это НЕ означает, что все назначения неверны;
это означает, что пока нет устойчивого основания выбрать конкретное имя остановки.

Есть условное согласие разных детекторов при фиксированной мягкой H0, например
№17 в сторону Медведково: «Улица Цандера»9/9пар, «Метро ВДНХ»9/9,
«Аргуновская улица»8/9; «МЦК Ростокино»5/6. Пары относятся к близким по времени
всплескам (±5с), коррелированы и используют общий prior/расписание. Это НЕ точность.
Для «Улицы Цандера» и «ВДНХ» эти назначения лежат в подбираемой первой четвёрке,
а не в проверяемом продолжении. Не назначаем им статус «нормально размеченных».

## Независимая проверка порядка столбцов №17

[route17-order-audit.json](route17-order-audit.json) содержит географический join
GTFS с историческими OSM-отношениями на 18.02.2025:540139v94 (из Медведкова),
540033v85 (из Останкина). Все26остановок каждого направления сопоставлены монотонно
с26из27GTFS-позиций, максимальные расстояния41.1/48.7м. Различие числа позиций связано
с терминальными точками. Архивные заголовки вручную сверены по всей цепочке с GTFS:
есть старые названия и дополнительная конечная позиция в прямом направлении,
но перестановок внутренних остановок не обнаружено. Проблемный переход
«Проезд Шокальского→Сухонская улица» подтверждён обоими независимыми источниками;
в обратном направлении порядок обратный. Нельзя исправить время перестановкой
этих двух столбцов без нарушения географии маршрута.
