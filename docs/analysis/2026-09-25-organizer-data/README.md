### Плотность, нули и маршрут 5

Labels содержат только положительные значения, без NULL, отрицательных величин
и повторных `(route,date,hour)`. История имеет 304 дня. Полная сетка всех десяти
маршрутов содержит 72 960 часов; отсутствуют 15 409 ключей (21,12%). Для девяти
наблюдаемых маршрутов — 8 113 отсутствующих ключей из 65 664 (12,36%).

Точная сверка с сырьём доказывает отсутствие успешных **строк в поставке** для
пропущенных ключей. Она не доказывает, что источник был исправен или маршрут
работал. В EDA-baseline отсутствующие ключи заполняются 0 именно как число событий
в поставке; в продуктовом pipeline нужны отдельные flags `source_coverage` и
`service_state`. Нельзя превращать недоставленный день в подтверждённый нулевой спрос.

Маршрут 5: одна сырая строка 29 октября 05:40:29, `validation_result=30`, то есть
отказ; успешных событий нет. В submission маршрут обязателен (1 464 строки).
Разумный первый кандидат — ноль с меткой «нет положительной истории», но это
не доказательство нулевого будущего потока. Уточнить у организаторов смысл этой
серии. WAPE маршрута с нулевой суммой факта не определён, а не «идеален».

Для остальных маршрутов полностью пустой route-day один: **50, 21 сентября**.
События/закрытие/сбой выгрузки требуют отдельного исследования; нулевой день
не удалён из оценки и не заполнен средним без evidence.

## 3. Измеренный baseline — что уже удаётся предсказывать

Эксперимент зафиксирован до запуска: сезонный профиль route × weekday × hour,
последние 1/4/8 недель; среднее либо медиана, все будущие дни предсказываются из
одной отсечки. Округление `numpy.rint`, nonnegative; никаких истинных будущих лагов.
Цель — проверить силу сезонного сигнала, не объявить production-модель готовой.
Кандидат для дальнейшей разработки должен улучшать зафиксированный baseline на
нескольких временных срезах; заранее предложенный порог — не менее 0,01 абсолютного
score на каждом основном срезе с разбором ухудшений отдельных маршрутов.

| Профиль | Июль–август, origin 01.07 (62 дня) | Сентябрь–октябрь, origin 01.09 (61 день) |
|---|---:|---:|
| Повтор последней недели | 0,81416 | **0,82319** |
| Среднее последних 4 недель | **0,81764** | 0,79028 |
| Среднее последних 8 недель | 0,80147 | 0,76760 |
| Медиана последних 4 недель | 0,81506 | 0,79348 |
| Медиана последних 8 недель | 0,79067 | 0,76055 |

Это WAPE-score по всей полной сетке, а не среднее route-score. На сентябрьском
срезе у повторения последней недели WAPE маршрута 50 — **36,06%**, маршрута 25 —
24,99%, у 17 — 10,51%. На июльском срезе у маршрута 7 WAPE **54,46%**. Средний
результат скрывает существенные локальные проблемы.

Baseline организаторов ≈0,48 заявлен для скрытого ноября–декабря; сравнивать его
напрямую с нашими 0,82 на другом периоде нельзя. Оценка скрытого периода не получена,
submission не отправлялся. После этого EDA сентябрь–октябрь уже не «нетронутый»
исследовательский holdout. Для отбора использовать rolling origins и вложенное
временное разделение, а финальный скрытый score остаётся внешней проверкой.

## 5. Как сделать ML, чтобы всё стыковалось

### Минимальная единая цепочка

```text
Неизменяемый ZIP + hash
  → raw reconciliation + cutoff 2025-11-01 00:00 Europe/Moscow
  → полная route/hour таблица + coverage flags + manifest
  → frozen-origin backtests → baseline / boosting candidate → quality gate
  → один versioned route-window artifact (10 × 61 × 24)
       ├→ submission.csv, exact template keys, nonnegative integers
       └→ atomic publisher → PostgreSQL → bounded API → текущий React UI
```

**Вход.** Для итераций обучения использовать проверенные labels: 57,5 тыс. строк,
после полной сетки 73 тыс., а не гонять 10 GB на каждой тренировке. Сырьё нужно
для reconciliation, качества и исследования аномалий. Сохранять hash, source
period, transform version, timezone, definition successful-validation count.

Существующий event contract требует stop/direction/vehicle/availability. Не
изобретать отсутствующие поля и не превращать агрегат в одно событие. Нужен
отдельный route-hour aggregate adapter и route-level feature entity. `ObservedAggregate`
— ориентир по семантике observed/missing, но его entity binding тоже надо проверить.
`input_date_time` нельзя использовать как availability. Для retrospective эксперимента
явно принять идеализированную доступность истории к cutoff; это не сертификат
online latency. Позже нужен источник delivery watermark.

**Модель.** Начать с уже измеренного weekly baseline и отдельной простой регрессии.
Первый ML-кандидат — общий по маршрутам градиентный бустинг с route/hour/weekday,
официальным производственным календарём, lead time и статистиками до origin.
Для двух месяцев удобнее direct модель: профиль последней недели, средние 4/8
недель, отношение недавнего уровня к предыдущему, calendar известной будущей даты.
Не использовать `y[t-24]` или `y[t-168]` как истинные значения после origin.
При обучении каждый пример имеет свой origin; все его признаки и обучающие labels
должны быть доступны до отсечки соответствующего fold. Никакого random split.

L1-loss согласуется с абсолютной ошибкой WAPE при фиксированном holdout;
Poisson — альтернативный кандидат для неотрицательных счётчиков. Сравнивать по
исходной шкале и с одинаковым округлением submission. Бустинг пока **не установлен,
не обучен и не признан лучше baseline**. GPU/GNN/OD не нужны для первого решения:
нет соответствующих target/графовых наблюдений, а сезонный сигнал уже силён.

**Проверка.** Несколько отсечек с 61-дневным горизонтом, например 01.05, 01.07,
01.09; для ровно 61 дня июльский fold заканчивать 30.08 (выше описательный опыт
на полных июле–августе имеет 62 дня). Отдельно считать первые 24 часа, первые
30/31 дней и дни 32–61. Срезы: route, hour/peak, weekday/holiday, monthly drift,
route5 и missing coverage. Фиксировать raw WAPE даже при score=0 и абсолютную
ошибку при нулевом знаменателе. Подбор на более ранних origins, итоговые параметры
фиксировать до следующей оценки. Не выбирать лучший профиль отдельно на каждом
будущем тестовом месяце по уже увиденному факту.

**Внешние факторы.** Первый приоритет — проверенный календарь рабочих/перенесённых
дней и каникул: future-known и дешёвый. Погодный факт ноября/декабря в backtest
с origin 1 ноября недопустим. Нужны архивы прогнозов с issue time или честный
сценарий/климатология, оценённый абляцией. Новость/ремонт должны иметь publication
и effective dates. Справочник с actual_date 2026 не доказывает, что признак был
известен осенью 2025. Каждый источник принимается только после measured uplift.

**Интервалы.** Оценить ошибки на прошлых origins по lead/route/time slice, калибровать
на отдельном прошлом окне. Проверить coverage и ширину на следующем срезе. Дневные
интервалы калибровать на дневной сумме: сумма почасовых нижних/верхних границ не
является автоматически интервалом нужного уровня. Пока это не сделано — bounds null.

### Необходимые изменения контрактов и serving

1. Добавить версионированный **route-window artifact**, сохранив `forecast.v1` для
   прежних потребителей. Явный `scope=route_all_directions`; stop/direction не
   подставляются. Отдельные `forecast_origin`, `data_cutoff`, `generated_at`,
   `prediction_start/end`, granularity, route set, target/unit, versions/hash.
   Валидатор: ровно 14 640 уникальных обязательных ключей, непрерывные московские
   часы, конечные значения ≥0, корректный cutoff, ни пропусков, ни лишних строк.
2. Сохранить истинный origin 01.11 для всей серии. Не публиковать декабрь как будто
   модель знала факты ноября. Для API нужны bounded day/month views одного issued
   bundle и выбор по покрытию даты. Текущий `forecast.v1` принимает лишь 24 часа /
   один календарный месяц по дням / год по месяцам; 61-day hourly туда не поместится.
3. Publisher TASK-029: explicit opaque canonical→integer serving registry, coherent
   all-route transaction, idempotency, draft→published после проверки, rollback
   active pointer. В backend route totals — строки `stop_id=NULL`; направление
   требует явного all-directions scope/marker. Не складывать total и directional rows.
4. Сейчас repository выбирает последний published run глобально по horizon. Простая
   публикация 61 отдельных дневных run скроет предыдущие дни, а частичный route run
   скроет остальные маршруты. Нужен bundle/coverage-aware selector; это отдельная
   проверяемая migration/API работа, не замена seed чисел.
5. Дневной экран читает 24 часа; месячный — суммы из того же почасового артефакта.
   CSV для жюри генерируется из артефакта, **не из текущего UI export**: у UI другая
   схема с provenance и выбранным окном. Проверка на одинаковые ключи/суммы обязательна.
6. Карта: route geometry с подписью маршрутного потока, reference date и mapping
   status. Stop filter/точечная heatmap при отсутствии stop predictions недоступны.
   Не размазывать поток равномерно по остановкам. Если импортировать справочники,
   сначала migration неуникальных имён и direction-aware route visits, затем crosswalk.
7. Годовой экран — ограничение данных или явно сценарный прогноз; двумя месяцами
   нельзя заполнить год. Отдельные поправки события/погоды — версия сценария поверх
   base run, без изменения базового submission; coefficients и единицы видимы.

## 6. Исследовательские основания

Источники просмотрены 25.09.2026:

- [Forecasting: Principles and Practice — time-series CV](https://otexts.com/fpp3/tscv.html):
  rolling origins и проверка многошагового горизонта. Здесь нужен 61-дневный forecast,
  а не только одношаговый тест; источник не обещает качество на трамваях.
- [scikit-learn — lagged features for forecasting](https://scikit-learn.org/stable/auto_examples/applications/plot_time_series_lagged_features.html):
  пример спроса на поездки и утечки при случайном разделении. Наши future lags
  требуют ещё более строгого ограничения, поскольку прогноз сразу на два месяца.
- [LightGBM — objectives](https://lightgbm.readthedocs.io/en/stable/Parameters.html):
  доступны L1, Poisson, quantile. Это обоснование кандидатов, не выбор зависимости
  и не подтверждение их преимущества. Dependency/license/advisory/size review
  потребуется перед добавлением пакета в проект.

## 7. Запуск и пределы доказательства

Использовался имеющийся bundled runtime: Python 3.12.14, pandas 2.2.3, NumPy 2.3.5,
openpyxl 3.1.5. Manifest/lock проекта не менялись. Скрипты исследовательские,
не импортируются online worker и не являются production adapter.

```sh
PYTHON=/Users/cute/.cache/codex-runtimes/codex-primary-runtime/dependencies/python/bin/python3
ARCHIVE='/Users/cute/MosTransport2026Hack/dataset (1).zip'
RESULTS=/tmp/tram-eda-rerun
$PYTHON profile.py "$ARCHIVE" "$RESULTS"
$PYTHON reconcile.py "$ARCHIVE" "$RESULTS"
$PYTHON baselines.py "$ARCHIVE" "$RESULTS"
```

Рабочий каталог команд — директория этого отчёта. Скрипты пишут только в указанную
RESULTS; raw ZIP остаётся read-only. `reconcile.py` проверяет точное равенство
объединённых raw counts и labels через assertions. Запускать без Python `-O`.
Время первого полного profile: train 101,32 s, test 26,99 s на текущей машине;
это локальный замер чтения ZIP и агрегации выбранных полей, не benchmark контейнера.

Не измерены: hidden score, качество occupancy/stop inference, event dedup identity,
реальные задержки источника, SLA API и production batch publication. Гипотезы о
причинах скачков и policy для route5 требуют дальнейшей проверки.

Результаты общего quality gate и handoff записаны в `HANDOFF.md` рядом.
