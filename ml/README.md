# TramFlow ML

Авторитетные требования: [постановка задачи](../docs/product/TASK.md) и [контракт датасета](../docs/product/DATASET.md). Приоритет — прогноз числа посадок по маршрутам и часам для конкурсного периода, затем день и месяц в интерфейсе. Годовой горизонт остаётся качественным сценарием. Остановочные и направленные величины, OD, мультимодальность и моделирование изменений выпуска требуют отдельной проверки.

Изолированное `uv`-окружение для offline-подготовки признаков, обучения и backtesting. Оно намеренно не импортируется backend-процессом.

```bash
make sync-ml
make dev-ml
make ml-check
```

## Конкурсный эксперимент по маршрутам и часам

Оцениваемая цель — число успешных валидаций для ключа `(route, date, hour)`.
Этот offline-путь отделён от синтетических контрактов `(route, direction, stop)`.
Для обучения используются метки организатора. Отсутствующие ключи считаются
нулями только после сверки сырых событий с метками. Архив, доказательство
сверки и записи отдельных пассажиров остаются вне Git. Пять CSV, которые
команда указала как загруженные, не содержат чувствительных данных; их сообщённые оценки и код
воспроизведения хранятся в [версионированном каталоге](competition_submissions/2026-09-27/README.md).

```bash
export TRAMFLOW_DATA_ARCHIVE=/absolute/path/to/dataset.zip
export TRAMFLOW_DATA_DIR=/absolute/path/to/private-output
uv run --package tramflow-ml tramflow-competition --archive "$TRAMFLOW_DATA_ARCHIVE" \
  reconcile --output "$TRAMFLOW_DATA_DIR/reconciliation.json"
uv run --package tramflow-ml tramflow-competition --archive "$TRAMFLOW_DATA_ARCHIVE" \
  --reconciliation "$TRAMFLOW_DATA_DIR/reconciliation.json" evaluate \
  --origin 2025-09-01 --model profile
uv run --package tramflow-ml tramflow-competition --archive "$TRAMFLOW_DATA_ARCHIVE" \
  --reconciliation "$TRAMFLOW_DATA_DIR/reconciliation.json" submit \
  --model calendar_profile --output "$TRAMFLOW_DATA_DIR/submission-calendar.csv"
```

`evaluate` моделирует полный горизонт 61 день × 24 часа от одной даты происхождения
прогноза и вычисляет WAPE-score организатора после округления до целого,
включая срезы по маршруту, месяцу и неделе горизонта. `submit` отклоняет
пропущенные, повторные, лишние ключи и нечисловые значения. Доступны модели
`profile`, `calendar_profile`, `calendar_weekday_blend`,
`calendar_robust_short`, `calendar_robust_28`, `calendar_robust_blend`,
`calendar_robust_hourshape`, `calendar_robust_28_hourshape`,
`calendar_robust_routeshape`, `calendar_robust_28_routeshape`, `hgb`, `catboost`,
`catboost_residual`, `catboost_relative`, `catboost_daily_relative`,
`fourier_ridge_daily` и `direct_extratrees_daily`. Отчёт содержит параметры,
версию признаков, хеш источника, число обучающих строк и покрытие графа.
В исходном CSV временная зона не указана: ключи маршрута, даты и часа считаются
московским гражданским временем без преобразования timestamp. Для CatBoost нужен
extra `boosting`; перед запуском выполните
`uv sync --all-packages --all-extras --locked`. Две модели дневных рядов
используют уже установленный scikit-learn и распределяют дневные суммы по
профилю дня недели/типа дня. На полных окнах они не превзошли этот профиль.

Устойчивые календарные кандидаты используют только плотные метки до каждой
даты происхождения прогноза. Они совмещают календарь типов дней, медианы
маршрут × час и ограниченный коэффициент уровня маршрута по недавней истории;
вклад коэффициента затухает на 61-дневном горизонте. `calendar_robust_blend`
усредняет прогнозы до округления. Девять полных исторических сравнений,
включая отвергнутые смеси CatBoost, приведены в [журнале экспериментов](../docs/experiments/route-hour-2025.md).
Варианты `hourshape` корректируют почасовые доли по прошлым окнам 28 и 56 дней
и точно сохраняют прогнозную сумму маршрут × день до округления. Варианты
`routeshape` объединяют типы дней внутри маршрута; относительно своих
неисправленных профилей они улучшили восемь из девяти полных дат происхождения.

### Ограниченные гибриды CatBoost и проверка смены режима спроса

`catboost_daily_bounded_50` и `catboost_daily_recency_ensemble_50` используют `calendar_robust_28_routeshape` как опору и обучают CatBoost на прошлых относительных маршрутно-дневных остатках. Первый вариант взвешивает наблюдения равномерно, второй усредняет равномерную модель и модель с 60-дневным периодом полураспада весов. Поправка ограничена 5% опоры; смесь с 50% опоры ограничивает итоговый вклад ML до 2,5%. Обучающие даты, признаки и метки строго предшествуют проверяемой границе. Это offline-модели; web worker не меняется. CatBoost 1.2.10 уже входит в extra `boosting`.

На полных 61-дневных окнах с началом в мае, июле, августе и сентябре локальные WAPE-score ансамбля равны `0.858811`, `0.839799`, `0.878375`, `0.892071`. Статистическая опора на соответствующих мае, июле и сентябре получила `0.865371`, `0.830310` и `0.891882`. Результат неоднороден. Публичный score `0.89195` подтверждается [снимком лидерборда](../docs/evidence/leaderboard-2026-09-27.png), но снимок не связывает его с конкретным CSV. [Версионированный локальный CSV ансамбля](competition_submissions/2026-09-27/README.md) имеет SHA-256 `edc07cca26ff21dd5228f744dea79940eb81a65c3ce5368aa743e2fc2fd0f11f`. Верхняя граница ML-поправки не способна исправить крупный разрыв объёма маршрута.

`guard` сопоставляет основную модель с кандидатами из того же реестра. Детектор уровня сравнивает 14 полных дней до границы с предшествующими 28 по одинаковым дням недели. Обе недавние недели должны сдвинуться в одну сторону минимум на 30%; маршруты с опорным дневным счётом ниже 20 исключаются. Детектор часовой формы сравнивает нормированные доли за 28 и 56 дней и требует согласованного сдвига полной вариации минимум `0.05` в обеих недавних половинах. Оба исключают исключительные даты `OFF`/`WORK` и неполные дни. Эти пороги — **предварительный фильтр, не калиброванные вероятности ошибки**. Неполная история подавляет сигнал, а не превращается в нулевой спрос.

```bash
uv sync --package tramflow-ml --extra dev --extra boosting --locked
uv run --package tramflow-ml tramflow-competition \
  --archive "$TRAMFLOW_DATA_ARCHIVE" \
  --reconciliation "$TRAMFLOW_DATA_DIR/reconciliation.json" \
  guard --origin 2025-08-28 --model catboost_daily_recency_ensemble_50 \
  --candidate calendar_robust_28_routeshape \
  --candidate calendar_robust_routeshape \
  --incumbent-window-days 28
```

JSON содержит сигнал, сравнение и выбор модели, а также ограничения: невиданные месяцы, маршрут без наблюдаемого спроса, коэффициент уровня вне `[0.75, 1.25]` и сдвиг сильнее 2,5% ML-поправки. Это признаки риска, а не прогноз ошибки и не разрешение переключиться. На `2025-08-28` коэффициенты реальных меток равны `1.712` для маршрута 7 и `0.678` для 50; оба выходят за диапазон опоры и границу ML. Сравнение обычных дней недели устранило прежний ложный майский сигнал праздников.

Кандидат оценивается на непересекающихся 61-дневных горизонтах, полностью закончившихся до проверки. Переключение требует двух прежних горизонтов со сдвигом в ту же сторону на том же маршруте, выигрыша общего WAPE-score не менее `0.002` на каждом, отсутствия общей потери на прочих проверенных горизонтах и улучшения всех сопоставленных маршрутов. При недостатке свидетельств остаётся основная модель. Детектор и оценщик подключены к общему контракту `decision_guard`. Для того же анализа в `submit` повторите `--guard-candidate` и задайте `--incumbent-window-days`; решение войдёт в JSON-квитанцию. Обычный `submit` не меняется. Недоступный CatBoost вызывает ошибку, а не тихую подмену. Фактическая погода ноября–декабря не может участвовать в решении на 1 ноября.

Метод окон мотивирован [rolling-origin validation](https://otexts.com/fpp3/tscv.html). [Исследование отбора при временном сдвиге](https://proceedings.mlr.press/v235/han24b.html) предполагает, что последующие исходы становятся наблюдаемыми; здесь независимых горизонтов мало и нет предыдущей зимы. Поэтому `guard` фиксирует недостаток доказательств. На 1 ноября нет сигнала уровня или часовой формы, но квитанция отмечает новые месяцы ноябрь/декабрь и отсутствие успешных валидаций маршрута 5. [Статья об ordered boosting](https://proceedings.neurips.cc/paper/2018/hash/14491b756b3a51daac41c24863285549-Abstract.html) касается сдвига при обучении, не устойчивости к будущей смене режима. Пороги и правило переключения требуют перспективной калибровки.

### Ретроспективный эксперимент с пространственной погодой

Необязательная модель `catboost_weather_relative` читает фактическую почасовую погоду Open-Meteo за 2025 год. Проверенные погодные данные и привязка остановок к ячейкам сохранены в `data/weather/2025/`. Воспроизведение экспорта из сохранённого снимка OSM:

```bash
uv run --package tramflow-ml python -m tramflow_ml.weather_spatial \
  --stops data/tram_stops.csv \
  --output-dir "$TRAMFLOW_DATA_DIR/moscow-weather-stopcells-2025"
uv run --package tramflow-ml python -m tramflow_ml.weather_spatial \
  --package-from "$TRAMFLOW_DATA_DIR/moscow-weather-stopcells-2025" \
  --output-dir "$TRAMFLOW_DATA_DIR/weather-package-2025"
uv run --package tramflow-ml tramflow-competition --archive "$TRAMFLOW_DATA_ARCHIVE" \
  --reconciliation "$TRAMFLOW_DATA_DIR/reconciliation.json" \
  --weather data/weather/2025/route-weather.csv.gz \
  evaluate --origin 2025-09-01 --model catboost_weather_relative
```

Экспорт сопоставляет 445 OSM-точек `stop_position` на конкурсных маршрутах с девятью ячейками API; уникальных имён остановок 225. Затем загружает год для каждой ячейки. `stops.csv` содержит прямую привязку; `zone-weather.csv.gz` — часы ячеек; `route-zones.csv` — число OSM-точек маршрута по ячейкам; `route-weather.csv.gz` — маршрутно-часовые признаки с весом по числу остановок. Экспорт содержит 78 840 ячейко-часов и 87 600 маршрутно-часовых строк, включая все 14 640 конкурсных ключей. Манифест фиксирует координаты, источник, даты, зону, SHA-256 и бюджет. Запуск использовал 45 HTTP-запросов (около 688 взвешенных вызовов); новые запуски ограничены 480 взвешенными вызовами/мин. Осадки относятся к предшествующему часу посадки по значению API в `H+1`.

Это **ретроспективный опыт с уже наблюдённой погодой**: погода проверочных сентября–октября и целевых ноября–декабря стала известна после соответствующих дат происхождения прогноза. Честный `submit` её отклоняет; score не доказывает качество прогноза на 61 день вперёд. Источник — [Open-Meteo Historical Weather](https://open-meteo.com/en/docs/historical-weather-api), атрибуция [CC BY 4.0](https://open-meteo.com/en/licence); [бесплатный тариф](https://open-meteo.com/en/pricing) рассчитан на некоммерческое использование. Привязка к ячейке точна для координат OSM 2026 года, но состав маршрутов OSM взят позднее, а организатор не дал истинную остановку посадки. Равный вес остановок — пространственная оценка, не наблюдаемое воздействие на пассажиров; полей отдельных валидаций в экспорте нет.

На сопоставимых локальных окнах `catboost_weather_relative` получил WAPE-score `0.815068` для июля–августа и `0.879774` для сентября–октября; `catboost_relative` без погоды — `0.817480` и `0.881740`. Чем больше WAPE-score, тем лучше; погодная ветка осталась экспериментом.

Необязательный `--direction-graph /path/to/features.csv` принимает таблицу с `;` и колонками `route;direction_id;available_at;valid_from;valid_to;stop_count;edge_count;length_m;source_version`. Источник должен быть известен до каждой даты происхождения. `valid_to` допустимо только при заранее объявленном окончании; для открытого изменения OSM используйте `9999-12-31`. `osm-inactive:` отменяет прежнее состояние после датированной деактивации; пустое `length_m` означает недоступную историческую геометрию, а `graph_length_available` отличает её от нуля. Признаки направления агрегируются по маршруту и сопровождаются покрытием. Перед принятием сравните одинаковые folds с таблицей и без неё.

```bash
uv run --package tramflow-ml tramflow-direction-structure \
  --histories /absolute/path/to/osm-histories \
  --source-index docs/analysis/2026-09-26-real-stops/sources.json \
  --output "$TRAMFLOW_DATA_DIR/osm-direction-structure.csv" \
  --report "$TRAMFLOW_DATA_DIR/osm-direction-structure-report.json"
```

Входной каталог должен содержать `relation-*-history.json` из индекса источников. Отчёт хеширует локальные файлы и отмечает расхождения с прежней загрузкой. `direction_id` — локальный ID relation OSM, а не GTFS-направление организатора. Соседство остановок не подтверждает рельсовую геометрию или фактическое движение. Граф 2026 года и современные справочники/расписания исключены из экспериментов с доступностью данных на даты 2025 года.

Перед добавлением модели зафиксируйте dataset version, временные split-границы, baseline, метрики и model card. Публикация результата в serving tables должна быть отдельным атомарным шагом.

Golden evaluation проверяет, что кандидат превосходит наивный baseline на каждом
горизонте и сохраняет согласованное покрытие интервалов:

```bash
uv run --package tramflow-ml tramflow-ml evaluate
```

## Синтетические фикстуры

`generate-synthetic` создаёт детерминированные фикстуры валидаций и телеметрии для проверки приёма, агрегации и оценки. Это искусственные числа посадок, **не** наблюдаемый московский спрос или наполненность. Крупные выходы оставляйте вне Git.

```bash
uv run --package tramflow-ml tramflow-ml generate-synthetic --output /tmp/synthetic-tiny
uv run --package tramflow-ml tramflow-ml generate-synthetic --mode million --output /tmp/synthetic-million
```

Каталог выхода до запуска не должен существовать. Порядок файлов: `entities.json`, `validations.jsonl`, `telemetry.jsonl`, `generation.json`, последним `manifest.json`. Без манифеста запуск считается неуспешным, даже если остался `.manifest.json.tmp`. `manifest.source_hash` — SHA-256 инвентаря имён, хешей и размеров первых четырёх файлов; сам манифест в хеш не входит. Одинаковые `--seed`, даты и периоды инъекций дают побайтово одинаковый результат независимо от часов и пути выхода.

| Параметр | По умолчанию | Контракт |
|---|---|---|
| `--events` / `--mode` | 64 для tiny, 1 000 000 для million | Число уникальных валидаций `N`; `--events` приоритетнее режима. |
| `--duplicate-every d` | 17 | Каждый `d`-й event повторяется; точных дублей `⌊N/d⌋`. `0` отключает. |
| `--late-every l` | 11 | У каждого `l`-го события `available_at` на день позже `event_at`, у прочих на минуту. `0` отключает. |
| `--telemetry-every k` | 5 | Одна строка телеметрии на каждый `k`-й event; `k >= 1`. |
| `--gap-every-days g` | 13 | Каждый `g`-й день в `[start, end)` не покрыт источником. `0` отключает, `1` запрещён. |

`unique_validations` исключает дубли. При `N > 1` события охватывают обе крайние покрытые даты. Покрытая дата без событий — наблюдаемый ноль; дата-пробел — отсутствие покрытия. Время записано в ISO-8601 с `Europe/Moscow`. `cell_totals` и `hour_totals` независимо суммируются в `N`. Порядок файловых строк соответствует времени события, но не гарантирует порядок доступности.

## Приём исторических данных

`ingest` нормализует фикстуры (`entities.json`, `manifest.json`, `validations.jsonl`, `telemetry.jsonl` либо `.csv` с `--format csv`) в события `data.v1` ограниченными возобновляемыми порциями (TASK-017, RQ-01).

```bash
uv run --package tramflow-ml tramflow-ml ingest --input /tmp/synthetic-tiny --output /tmp/ingest-tiny
uv run --package tramflow-ml tramflow-ml ingest --input /tmp/synthetic-million --output /tmp/ingest-million --chunk-size 10000
```

Выход: канонические `validations.jsonl` и `telemetry.jsonl` с московским временем; `quarantine.jsonl` с полями `stream`, `row_index`, `reason`, `detail`, `raw` и `raw_base64` только для невалидного UTF-8; последним `manifest.json` версии `ingestion.v1`. Манифест содержит версию нормализации, SHA-256 и размер каждого входа, исходный манифест, счётчики потоков и `output_hash`. Результат не зависит от текущего времени и путей.

Для каждого потока действует `input_rows == valid + duplicates + quarantined`. Повтор `event_id` с тем же нормализованным содержимым — дубль (остаётся первый); с иным содержимым — `conflicting_duplicate` в карантине. Код выхода `1` означает нарушение равенства, `2` — ошибку входа или использования. Коды причин: `decode_error`, `missing_field`, `invalid_type`, `invalid_value`, `invalid_timestamp`, `availability_before_event`, `unknown_entity`, `conflicting_duplicate`.

После порции выходы сбрасываются, индекс `event_id` в SQLite фиксируется, `checkpoint.json` атомарно заменяется. Повтор той же команды возобновляет работу и даёт побайтово одинаковый выход; другой хеш входа, версия нормализации, адаптер, формат или размер порции отклоняются. Адаптер сравнивается по имени: изменив `ColumnAdapter`, задайте новое имя. Некорректный `ingestion-checkpoint.v1` отклоняется с кодом `2`; полный каталог с `manifest.json` не перезаписывается. `checkpoint.json` и `dedup.sqlite` удаляются после записи манифеста. Память ограничена `--chunk-size` и 8 MiB кэша SQLite; для запуска на миллионе событий зафиксировано 57 MB пиковой RSS, как и на 100 000.

CSV требует одну запись на физическую строку: переносы в кавычках не поддержаны, поскольку возобновление идёт по смещению байтов. `ColumnAdapter` задаёт колонки, константы, `timestamp_format` и `assume_timezone`; BOM UTF-8 перед заголовком игнорируется. CLI пока предоставляет лишь адаптер `synthetic`; произвольный CSV доступен через Python API `ingest(IngestionConfig(..., source_format="csv", adapter=...))`. Адаптеры организатора требуют реальных образцов.

## Сопоставление идентификаторов

`tramflow_ml.identity` сопоставляет события с каноническим каталогом через явную версионированную таблицу соответствий и правила времени источника. Это Python API без CLI. Каждая запись получает `AlignedEvent` с результатом `Matched` (`exact_id`, `name_route_direction`, `geo_nearest`), `Unmatched(reason)`, `Ambiguous(field, candidates)` или `Stale(lag_seconds)`; догадок вместо ключей нет.

```python
from tramflow_ml.identity import (
    AlignmentConfig, CanonicalCatalog, SourceEvent, align_events, load_crosswalk, quality_report,
)

catalog = CanonicalCatalog.from_dict(entities_json)          # entities.json shape (data.v1)
crosswalk = load_crosswalk(crosswalk_json, catalog)          # unknown canonical ids raise
config = AlignmentConfig.from_dict({"clocks": {"validations": {"timezone": "UTC"}}})
aligned = align_events(catalog, crosswalk, config, source_events)
report = quality_report(crosswalk, aligned).to_dict()
```

Таблица содержит `crosswalk_version`, совпадающий с каталогом `entity_version`, словари `routes`, `directions`, `stops`, уточнённые по маршруту/направлению `stop_names`, координаты `stop_positions` и полуоткрытые интервалы назначений `vehicles` `[valid_from, valid_to)`. Неизвестные канонические ID отклоняются.

| Ситуация | Результат |
|---|---|
| Одинаковое имя двух остановок без уточнённого `stop_names` | `Ambiguous("stop", …)` |
| Направление отсутствует или неизвестно | `Unmatched`; направление не выводится по остановке |
| Остановка повторяется без `stop_sequence`/`previous_stop_id` | `Ambiguous("stop_sequence", …)` |
| Назначение вагона противоречит маршруту источника | `Unmatched("vehicle_route_conflict")` при наличии действующего назначения; отсутствие назначения не запрещает соединение |
| GPS — ключ, а `abs(fix_at - event_at)` превышает `gps_staleness_seconds` | `Stale`; точный `stop_id` соединяется независимо от GPS |
| Наивное время попадает в пробел либо неоднозначность DST зоны источника | `Unmatched("nonexistent_local_time")` / `Unmatched("ambiguous_local_time")`, без догадки об instant |
| Две остановки попадают в `geo_tolerance_metres` | `Ambiguous`; ни одной — `Unmatched` |
| `available_at` отсутствует без `availability_lag_seconds` | `Unmatched("availability_missing")` |

Наивное время читается в зоне источника, `offset_seconds` применяется в UTC, результат выдаётся в `Europe/Moscow`. `AlignedTime` хранит исходные и исправленные `event_at`/`available_at` и флаг `service_day_shifted`. Сырые строки не изменяются. Отчёт качества разбивает потоки по `source_id`; доли исходов суммируются в 1, виды совпадений и причины отказа даны счётчиками. Реальные идентификаторы, имена и GPS-допуски до изучения организаторских данных не сертифицированы.

## Построение признаков

`tramflow_ml.features` преобразует события `data.v1` в таблицу для каждого горизонта (TASK-019, RQ-01–03). Это Python API; подключение CLI и общего пайплайна — отдельная задача. Строка соответствует `(route_id, direction_id, stop_id)` и календарной корзине; заголовок фиксирует версию признаков, политику, происхождение прогноза и границу доступности.

```python
from tramflow_ml.features import (
    YEAR_MONTH, CoverageCalendar, FeatureRequest, build_features,
    load_entity_keys, load_observations,
)

observations = load_observations(ingest_dir / "validations.jsonl")
coverage = CoverageCalendar.from_range(date(2024, 1, 1), date(2026, 1, 1), gaps=gap_dates)
table = build_features(FeatureRequest(
    policy=YEAR_MONTH,
    origin=datetime(2025, 1, 1, tzinfo=MOSCOW),
    entities=load_entity_keys(fixture_dir / "entities.json"),
    observations=observations,
    coverage=coverage,
    target="synthetic_boardings",
    unit="event_count",
))
```

Ключ корзины включает полуоткрытый интервал `[bucket_start, bucket_end)` в `Europe/Moscow`. Направление сохраняется; повторное посещение остановки на кольце агрегируется в одну ячейку.

| Политика | Горизонт | Корзины | Лаги | Окна | Сезонность |
|---|---|---|---|---|---|
| `day/hour` | день | 24 часа | 1, 2, 24, 48, 168 ч | 24, 168 ч | 4 × 24 ч |
| `month/day` | месяц | 28–31 день | 1, 7, 14, 364 д | 7, 28 д | 4 × 7 д |
| `year/month` | год | 12 месяцев | 1, 2, 3, 12 мес | 3, 12 мес | 3 × 12 мес |

Граница `C` выводится из происхождения прогноза; `cutoff_lead_buckets` сдвигает её назад для поздно публикуемого источника. Событие попадает в признаки только при `event_at < C and available_at <= C`; историческая корзина используется только при `bucket_end <= C`. Поэтому текущая корзина отсутствует, а не считается частичной; `lag_1h` для `day/hour` определён только для первого прогнозного часа. Скользящие окна привязаны к последней полной исторической корзине. Метки `target_value` берутся из полной серии и не входят в `feature_digest`.

`CoverageCalendar` может хранить момент публикации каждой даты. Исторический вид `as_of(C)` не считает ещё не опубликованный день наблюдаемым нулём; метки читаются из `complete()`. Гранулярность механизма — гражданская дата: если строки по уже опубликованной дате поступают позднее, отдельные корзины могут казаться нулевыми. Формат построчной публикации организатор не предоставил.

Отсутствие кодируется `None`, а не `0.0`: `coverage="missing", value=None` при отсутствии доступных дат; покрытая дата без событий — `coverage="observed", value=0`. Неизвестная вместимость тоже `None`. Для многодневных корзин признаки `*_units` показывают долю доступных дат на границе `C`; эти колонки нужны для `year/month`, где частично покрытый февраль не должен выглядеть месяцем с низким спросом. `covered_units`/`total_units` есть у каждой `AggregateCell`.

Часовые шаги идут по UTC-инстантам, дневные — по гражданским датам, месячные — по календарным месяцам. Месяц не аппроксимируется 30 днями, год — 365. Московские исторические переходы DST дают 23/25 часов 27.03.2011 и 26.10.2014; после 2014 DST нет. Неоднозначная либо несуществующая московская полночь отклоняется, а не угадывается. Это строже `contracts/calendar_v1.forecast_buckets`. Цели ограничены `synthetic_boardings` и `validation_count` в `event_count`: одна запись события не становится оценкой наполненности вагона.

Сортировка сущностей, корзин и признаков делает `FeatureTable.digest` воспроизводимым SHA-256 канонического JSON. На маленькой фикстуре 64 уникальных события и 12 сущностей; часовая агрегация совпадает со всеми 64 `cell_totals` файла `generation.json`. Тест `test_the_published_digest_still_describes_the_committed_fixture` закрепляет хеши `7e412bb0…` (`day/hour`), `b3ad914c…` (`month/day`) и `58e57f49…` (`year/month`); последний сменил прежнее `408d4580…` после исправления отсечения `*_units`. Политики корзин, лагов, окон, сезонности и задержек — настройки команды, не подтверждённые организатором. Покрытие реальных данных должно исходить из утверждения об их полноте, а не из счёта строк. Историческая погода и события не входят в признаки до доказательства доступности на дату происхождения; `is_weekend` не является признаком праздника.

## Хронологическая проверка со сдвигом происхождения

`tramflow_ml.backtest` создаёт общий набор хронологических окон для кандидата и baseline и манифест эксперимента (TASK-020, RQ-02). Это Python API; CLI и подключение пайплайна относятся к TASK-058.

```python
from tramflow_ml.backtest import BacktestConfig, BacktestData, FoldRules, run_backtest
from tramflow_ml.features import MONTH_DAY, YEAR_MONTH, CoverageCalendar, load_entity_keys, load_observations

config = BacktestConfig(
    rules=(FoldRules(policy=MONTH_DAY), FoldRules(policy=YEAR_MONTH)),
    target="synthetic_boardings",
    unit="event_count",
)
data = BacktestData.of(
    load_entity_keys(fixture_dir / "entities.json"),
    load_observations(ingest_dir / "validations.jsonl"),
    CoverageCalendar.from_range(date(2024, 1, 1), date(2026, 1, 1), gaps=gap_dates),
)
outcome = run_backtest(config, data, [candidate, baseline])   # models, in the caller's order
outcome.passed, outcome.reasons, outcome.manifest.manifest_hash
```

Модель реализует `name`, `version`, `predict(fold, data) -> Sequence[float]` (`FoldModel` — `Protocol`). Ей передаются только обрезанные по границе `FoldView`, `FoldData`, наблюдения train/validation и строки признаков без меток. Полный ряд, календарь покрытия и покрытие будущих меток не выдаются. Маппинги строк закрыты через `MappingProxyType`, чтобы одна модель не изменила вход другой. Прогнозы должны быть конечными и неотрицательными.

Для происхождения `O`: test — `[O, horizon_end(O))`; граница `C` — `O` минус задержка политики и embargo; validation — заданное число полных периодов до последней границы `<= C`; train — от первой целой корзины до начала validation за вычетом embargo. Инвариант `train.end <= validation.start < validation.end <= C <= O < test.end` проверяется при создании. Соседние test-окна не пересекаются. `day` по `calendar.v1` означает 24 прошедших часа; при историческом DST следующая дата происхождения может прийтись на 01:00 местного времени, сохраняя непрерывность. Embargo реализуется через эффективную политику признаков, без повторения логики отсечения.

Каждое потенциальное происхождение либо образует fold, либо получает первую причину отказа: `horizon_beyond_data`, `incomplete_labels`, `diluted_labels`, `insufficient_train_history`. Числа отказов входят в хеш fold. `run_backtest` возвращает `evaluated`, `insufficient_history` или `insufficient_signal`; пустой набор не может пройти. `passed` говорит только о пригодности набора окон, **не** о качестве модели.

Пороги пока конфигурация команды. `minimum_origins=3`; столько же по умолчанию требует `minimum_origins_with_demand`. `minimum_train_buckets` равен наибольшей глубине объявленных лагов, окон и сезонов: 168 часов, 364 дня, 36 месяцев; считаются именно покрытые корзины. `minimum_label_unit_ratio=1.0` требует полной истины test-окна. Embargo равен нулю: граница и календарь публикации уже учитывают доступность. Его следует увеличить при целевой величине, размазанной по окну, или при пересмотре уже опубликованных дат.

Четыре SHA-256 канонического JSON фиксируют конфигурацию, данные, fold и полный манифест. В последний входят имена и версии моделей **в порядке сравнения**. Временные метки нормализуются через UTC; часы запуска и абсолютные пути исключены. Тесты доказывают отсутствие утечки: события после горизонта не меняют признаки и разбиение; события внутри test изменяют только метки; перенос `available_at` через границу действительно меняет признаки. Оба кандидата видят идентичные объекты fold и data.

На синтетическом пути (`synthetic → ingestion → features → folds`) результаты с 12 сущностями и настройками по умолчанию:

| Фикстура | Горизонт | Допущено | Отклонено |
|---|---|---:|---|
| 2024–2026, 64 события, пробел каждые 13 дней | день | 667 | 56 `incomplete_labels`, 8 `insufficient_train_history` |
| та же | месяц | 0 | 24 `incomplete_labels` |
| та же | год | 0 | 2 `diluted_labels` (338/366 и 337/365 дат) |
| 2024–2026, 2 000 событий, без пробелов | день | 723 | 8 `insufficient_train_history` |

## Профилирование входа

`intake` читает **образец** данных и описывает его схему, покрытие и возможность поддержать горизонты до построения адаптера (TASK-039, RQ-01–03; маппинг — TASK-049/TASK-050).

```bash
uv run --package tramflow-ml tramflow-ml intake --input /tmp/synthetic-tiny
uv run --package tramflow-ml tramflow-ml intake --input /tmp/sample --profile sample.json \
  --catalog /tmp/sample/entities.json --output /tmp/intake-report.json
```

Вход открыт только для чтения (`rb`); `--output` внутри входного каталога отклоняется. Отчёт идёт в stdout и при необходимости в отдельный файл. По `validations` и `telemetry` он показывает физические, читаемые и нечитаемые строки, присутствие и форму канонических полей, дубли `event_id`, диапазон дат и покрытие сопоставления. `supportability` оценивает только возможности наблюдаемого диапазона и покрытия.

| Класс | Поля | Публикуемые сведения |
|---|---|---|
| `identifier` | `event_id`, `route_id`, `direction_id`, `stop_id`, `vehicle_id`, `entity_version`, `source_version` | наличие, число уникальных, длины, класс символов; **не значения** |
| `timestamp` | `event_at`, `available_at` | наличие, ошибки разбора, первый/последний момент по Москве |
| `measure` | `stop_sequence`, `latitude`, `longitude` | наличие, ошибки, выход за контракт, минимум/максимум; для целого поля — сумма |
| `enumerated` | `schema_version`, `target`, `unit`, `synthetic` | счётчики разрешённых значений и общий `other` |

Идентификаторы не печатаются даже в примерах ошибок или хешах; накопитель хранит только 8-байтовые дайджесты. Значение вне разрешённого списка печатается лишь как `other`. Заголовок CSV распознаётся только если **все** ячейки строки выглядят как идентификаторы (`str.isidentifier`); иначе **вся** строка выводится по форме и позиции, включая похожие на имена ячейки. Для JSON Lines то же правило применяется к набору ключей. Это предотвращает вывод строк данных, ошибочно принятых за заголовки, но полностью состоящая из слов строка без заголовка всё ещё может быть напечатана. Заголовок с пробелом/дефисом показывается по форме; явный профиль позволяет сопоставить его поля.

Отчёт всё же содержит имена файлов и похожие на слова имена колонок из схемы, `entity_version` и текст проверки каталога, а также реальные минимумы/максимумы числовых полей, включая GPS. Поэтому персональные данные нельзя сопоставлять с `measure`. По умолчанию поле сопоставляется только при **точном** совпадении канонического имени либо через явный профиль. По похожести имени или позиции сопоставления нет. Встроенный профиль `canonical` ожидает `validations.jsonl`/`telemetry.jsonl` или `.csv`; наличие обеих форм отклоняется как неоднозначность.

Пример `intake-profile.v1`:

```json
{
  "schema_version": "intake-profile.v1",
  "name": "alternate-fixture",
  "source_format": "csv",
  "files": {"validations": "boardings.csv", "telemetry": "positions.csv"},
  "columns": {"event_id": "row_key", "event_at": "happened", "stop_id": "platform_code"},
  "constants": {},
  "timestamp_format": "%d.%m.%Y %H:%M:%S",
  "assume_timezone": "Europe/Moscow"
}
```

`columns` задаёт соответствие каноническое поле → колонка; `constants` — пропущенное поле с общим значением; `timestamp_format` — формат `strptime` или `null` для ISO-8601; `assume_timezone` — зона наивного времени. `has_header=false` разрешает CSV без заголовка, где колонки называются `column_1`, `column_2` и так далее. Один профиль обслуживает оба потока, поэтому разные схемы двух CSV без заголовков одним профилем не описываются. Заявленная отсутствующая колонка CSV отклоняется сразу; отсутствующий ключ JSON Lines отражается как `missing_rate: 1.0` и `declared_columns_never_seen`. Необъявленное обязательное поле, не встреченное ни в одной строке, вызывает список требуемых соответствий. При ошибке отчёт перечисляет найденные и неиспользованные колонки, соответствия, константы и шаблон профиля с `null` для незаполненных полей.

Покрытие сопоставления использует словарь `identity`: `matched` по виду, `unmatched` по причине, `ambiguous`, `stale`. Проверка ведётся против `identity_crosswalk`, где ID соответствует самому себе; для другой системы ID это расстояние от её ключей до каталога, а **не реальная доля успешного соединения**. Строки без `event_id` или разбираемого времени учитываются как `unalignable`. Без каталога указано `"measured": false`, не нуль.

Для политики горизонта максимальная требуемая история — `max(max(P.lags), max(P.rolling_windows), P.season_step * P.season_periods)` корзин плюс 24 часа, 31 день либо 12 месяцев будущего периода. `supportability` требует достаточно **полных** корзин и строк хотя бы на половине гражданских дат диапазона. Граничные неполные корзины не считаются. Это верхняя оценка пригодности, не план fold и не доказательство качества. Измерение числа покрытых дат не доказывает, что цель организатора именно такая. `MIN_COVERAGE_RATIO` — порог, не замер.

Числовые поля проверяются как в `ingestion.normalize`: `stop_sequence` — неотрицательное целое, широта ±90, долгота ±180. `0.0` для целочисленного поля нормализуется к `0`; иначе одинаковая CSV/JSON-информация дала бы ложный конфликт дублей. На поток действуют `rows == readable + unreadable`, `readable == unkeyed + distinct_keys + repeated + conflicting`, а при каталоге `readable == join total + unalignable`. Коды выхода совпадают с `ingest`: `0` успех, `1` нарушение равенств, `2` неверный вход/схема. Отчёт детерминирован, без текущего времени и абсолютных путей; память растёт с числом уникальных ключей, не строк. Для огромного архива профилируйте часть: полномасштабный `ingest` использует SQLite.

## Срезы качества и интервалы

`tramflow_ml.slices` проверяет, где именно кандидат ошибается. `make ml-eval` режет только по горизонту; `BacktestOutcome.passed` говорит о пригодности окон, а не точности. Этот пакет не меняет `evaluation.py` и принимает `ScoredPoint` — уже сопоставленный прогноз и исход с сущностью, горизонтом, корзиной, fold, целью, единицей и необязательными событием, интервалом, baseline, вместимостью. Он не строит прогноз и не выдумывает отсутствующие атрибуты (`None`).

### Оси срезов

Каждая точка попадает во все применимые оси. Они выводятся из точки, а не передаются извне, поэтому переименовать провальный срез нельзя.

| Ось | Значение | Ограничение |
|---|---|---|
| `overall` | `all` | всегда есть и обязателен |
| `horizon` | `day`/`month`/`year` | горизонт |
| `fold` | `fold_id` | одно происхождение, порог числа folds не применяется |
| `route` | `route_id` | оба направления вместе |
| `direction` | `route_id\|direction_id` | направление без маршрута неоднозначно (ADR-0006) |
| `stop` | `stop_id` | физическое место для обоих направлений |
| `entity` | `route_id\|direction_id\|stop_id` | ключ прогноза |
| `daypart` | `morning_peak`/`evening_peak`/`offpeak` | только часовые корзины |
| `route_daypart` | `route_id\|daypart` | маршрут × часть дня |
| `entity_daypart` | `route_id\|direction_id\|stop_id\|daypart` | ключ × часть дня |
| `event` | тег вызывающего кода | только если он задан |

`MORNING_PEAK_HOURS` — 07–09, `EVENING_PEAK_HOURS` — 17–19 по Москве. Месячные/годовые точки не получают искусственный `daypart`. Срез `fold` по определению содержит одно происхождение, поэтому `MIN_FOLDS_FOR_GATE` к нему не применяют, но минимум выборки остаётся. Пересечение `entity_daypart` нужно против разбавления: в синтетическом примере ошибки 100% на одной остановке вечером общая WAPE равна `0.033`, а пересечение показывает `1.0`. `fold × horizon` не создаётся, поскольку `fold_id` уже содержит горизонт (`f"{horizon}@{origin}"`).

Ограничение фиксированных осей: подгруппа с теми же route/direction/stop/daypart/horizon/fold, что и хорошо предсказанные точки, останется разбавленной во всех срезах. Без `entity` нельзя построить route/direction/stop и их пересечения; направление по ADR-0006 не выводится. Прохождение контроля не доказывает отсутствия таких подгрупп.

### Метрики и единицы

Ошибки вычисляются `backtest.metrics.fold_metrics`; folds объединяются по суммам, а не средним WAPE.

| Метрики | Единица |
|---|---|
| `actual_total`, `error_total`, `mae`, `mean_actual`, `mean_width`, `mean_interval_score` | единица цели |
| `wape`, `baseline_wape`, `coverage`, `level`, `relative_interval_width`, `actual_overload_rate`, `predicted_overload_rate` | `ratio` |
| `samples`, `folds`, `covered`, `actual_overloaded`, `predicted_overloaded` | `count` |

Каждый срез и запись отказа несут `samples`, `folds` и карту `units`; единица цели не применяется к WAPE. Вложенные `interval` и `overload` несут число образцов, но наследуют число folds среза. Сравнение с baseline возможно, только если он есть у **всех** точек среза; отсутствие фиксируется с числом строк в `baseline_absent_reason`. Аналогично устроены `interval_absent_reason` и `overload_absent_reason`.

### Почему одного покрытия интервала недостаточно

Интервал `[0, 10000]` при спросе 100 даёт идеальное покрытие без практической пользы. Поэтому вместе с ним выводятся средняя ширина и **интервальная оценка Винклера**:

```text
IS = (upper - lower) + (2/α)·(lower - y)·1{y < lower} + (2/α)·(y - upper)·1{y > upper}
```

Здесь `α = 1 - level`; меньше лучше, единица совпадает с целью. Для двенадцати значений спроса 100 интервалы `[90, 110]` и `[0, 10000]` оба дают покрытие `1.0`, но оценки `20` и `10000`. Смешение разных номинальных уровней или методов, как и частично отсутствующие интервалы, подавляет интервальные метрики с явной причиной. Проверка `MIN_INTERVAL_LEVEL` не позволяет объявить настолько низкий уровень, чтобы требования покрытия и штраф за промах стали пустыми; `GateThresholds` требует `MAX_COVERAGE_SHORTFALL < MIN_INTERVAL_LEVEL`.

### Нулевой спрос и малые выборки

При нулевой сумме фактов WAPE не определена: `wape: null`, статус `insufficient_signal`, без искусственного epsilon; MAE остаётся определённой. Ошибка такой точки всё равно входит в числитель общей WAPE. `evaluation.py` для curated golden case вместо этого вызывает ошибку; оба поведения заданы явно. Ниже `MIN_SAMPLES_FOR_GATE` статус `insufficient_samples`, ниже `MIN_FOLDS_FOR_GATE` — `insufficient_history`. Метрики остаются видимыми, но срез не участвует в вердикте. Отчёт также считает все неоценённые срезы, причины и худшую WAPE среди них, чтобы их нельзя было скрыть через малую выборку или одно происхождение.

### Перегрузка и неизвестная вместимость

`overload` выводится лишь для цели `onboard_load` в `passengers`, когда **каждая** точка среза имеет положительную известную вместимость. По умолчанию вместимость здесь не придумывается. Online-путь сейчас иначе выдаёт `ForecastPointModel.capacity=180.0` при неизвестном значении; данный пакет этот дефект не повторяет. Перегрузка **показывается, но не влияет на gate**: текущий слой признаков выдаёт только `event_count`, и ни один реальный срез репозитория пока не несёт цели наполненности. Устанавливать порог до появления такой цели было бы фиктивной строгостью.

### Вердикт

```text
passed = нет нарушения и нет недоказанного обязательного среза
```

Каждый срез со статусом `evaluated` проверяется. Обязательный срез должен существовать и быть оценимым; отсутствие, недостаточная выборка/история и нулевой спрос дают `unproven`, а неизвестная ось отклоняется как ошибка конфигурации. `overall` всегда обязателен. Gate ограничен объявленными осями и минимумами; перегрузка не проверяется. Прохождение означает лишь отсутствие видимого нарушения этих правил. Например, 48 идеальных внепиковых точек и 12 плохих вечерних дают общую WAPE `0.18`, но вечерний срез `0.9` проваливает `MAX_WAPE=0.4`.

### Временные пороги

| Константа | Значение | Проверка |
|---|---:|---|
| `MIN_SAMPLES_FOR_GATE` | 12 | минимальное число точек |
| `MIN_FOLDS_FOR_GATE` | 2 | число разных происхождений |
| `MAX_WAPE` | 0.40 | WAPE среза |
| `MAX_WAPE_RATIO_TO_BASELINE` | 1.0 | отношение к baseline среза |
| `MAX_COVERAGE_SHORTFALL` | 0.10 | допустимый недобор покрытия |
| `MAX_INTERVAL_SCORE_TO_MEAN_ACTUAL` | 2.0 | интервальная оценка / средний спрос |
| `MIN_INTERVAL_LEVEL` | 0.8 | номинальный уровень |
| `MIN_INTERVAL_SCORE_ALLOWANCE` | 8.0, в единицах цели | абсолютный допуск интервальной оценки |

**Пороги не сертифицированы:** подобраны на синтетических точках. Отчёт печатает `"certified": false`; каждое нарушение содержит имя порога, порог, наблюдаемое значение и поддержку. Отношение интервальной оценки к среднему спросу несовершенно: при малом спросе правильный интервал может выглядеть широким, поэтому добавлен абсолютный допуск; при среднем спросе 1000 интервал `[60, 1940]` всё ещё проходит и требует ручной оценки `relative_interval_width`. Надёжное решение потребует сравнения с эталонным интервалом (TASK-021).

Точки канонически сортируются перед суммированием; повтор `(entity, horizon, bucket, fold)` отклоняется. В payload нет часов запуска или абсолютного пути; `SliceReport.digest` — SHA-256. **В pipeline пакет ещё не подключён:** `make ml-eval` запускает прежний golden gate, а использования `tramflow_ml.slices` есть только в тестах. Катастрофический срез пока не провалит `make check` через этот пакет; подключение к публикации — TASK-058. Синтетические примеры проверяют механизм, но не точность прогноза Москвы, калибровку интервалов или пороги. Для этого нужны реальные данные на нетронутых хронологических срезах (TASK-051).
